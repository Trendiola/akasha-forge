# Akasha Forge — Desktop Shell Build (AF-DESKTOP-006, Tauri 2)

> **This Tauri shell was authored on headless Linux aarch64 and was NOT compiled
> or run natively here** (no Rust/WebKit/display in the Emergent container). The
> React build, TypeScript check, config validity, and the full backend
> **sidecar-lifecycle contract** were validated in this environment
> (`backend/tests/desktop_tauri_lifecycle.py`). The native window + Rust compile
> and the Windows `.exe` **must be built/validated on Windows.**

The desktop app is a **Tauri 2** shell that launches the frozen backend
(AF-DESKTOP-005) as a managed child process, waits for `/api/health`, injects
`window.__AKASHA_RUNTIME_CONFIG__`, then loads the existing React UI.

## Project layout
```

  src-tauri/
```

## Prerequisites (Windows 10/11 64-bit)

1. **Node.js 20.x + Yarn 1.22**
   - https://nodejs.org/ → `npm i -g yarn`
2. **Python 3.11.x** (for building the backend sidecar) — "Add to PATH".
3. **Rust (stable, MSVC toolchain)**
   ```powershell
   # https://www.rust-lang.org/tools/install  (rustup-init.exe)
   rustup default stable-x86_64-pc-windows-msvc
   ```
4. **Microsoft C++ Build Tools** (MSVC) — "Desktop development with C++"
   from the Visual Studio Build Tools installer.
5. **WebView2 Runtime** — preinstalled on Windows 11 / recent Windows 10. If
   missing: https://developer.microsoft.com/microsoft-edge/webview2/ (Evergreen
   Runtime). Tauri 2 renders through WebView2; no bundled browser.
6. **Tauri CLI** — already added to the frontend as a dev dependency
   (`@tauri-apps/cli` v2). Use `yarn tauri ...`.

## Build steps (Windows)

### 1. Install frontend dependencies
```powershell
cd frontend
yarn install
```

### 2. Build the backend sidecar (AF-DESKTOP-005)
Follow `backend/BUILD_DESKTOP.md`, i.e.:
```powershell
cd ..\backend
py -3.11 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install -r requirements.txt
pip install emergentintegrations --extra-index-url https://d33sy5i8bnduwe.cloudfront.net/simple/
pip install pyinstaller
pyinstaller build.spec --noconfirm --clean
# -> backend\dist\AkashaForgeBackend\AkashaForgeBackend.exe (+ _internal\)
```

### 3. Place the sidecar where Tauri bundles it
Copy the **entire one-dir folder** into the Tauri resources dir:
```powershell
cd ..\frontend
Remove-Item -Recurse -Force src-tauri\resources\backend\AkashaForgeBackend -ErrorAction Ignore
Copy-Item -Recurse ..\backend\dist\AkashaForgeBackend src-tauri\resources\backend\AkashaForgeBackend
```
Required final layout (name matters):
```
src-tauri\resources\backend\AkashaForgeBackend\
    AkashaForgeBackend.exe      <-- resolved at runtime
    _internal\ ...
```
> At runtime the shell resolves
> `<resource_dir>\resources\backend\AkashaForgeBackend\AkashaForgeBackend.exe`.
> (Because AF-005 is a PyInstaller **one-dir** build, the sidecar ships as a
> bundled **resource folder**, not a single-file Tauri `externalBin`.)

### 4. Build the React frontend
`tauri build` runs this automatically via `beforeBuildCommand: "yarn build"`,
but you can run it manually:
```powershell
yarn build      # -> frontend\build\
```

### 5. Generate app icons (once, or when the icon changes)
```powershell
yarn tauri icon src-tauri/app-icon.png
# -> populates src-tauri/icons/ (icon.ico, 32x32.png, 128x128.png, icon.icns, ...)
```

### 6. Build the desktop app
```powershell
yarn tauri build
```

### Expected Windows outputs
```
frontend\src-tauri\target\release\Akasha Forge.exe            # the app executable
frontend\src-tauri\target\release\bundle\nsis\*-setup.exe     # installer (AF-DESKTOP-008 territory)
frontend\src-tauri\target\release\bundle\msi\*.msi            # installer (AF-DESKTOP-008 territory)
```
> The bundler emits installers because `bundle.targets = "all"`; **AF-DESKTOP-008**
> owns final installer configuration. To produce just the runnable app while
> iterating, use `yarn tauri build --no-bundle`.

## Version consistency
The **release version of record is `version` in `src-tauri/tauri.conf.json`**
(currently `2.0.0`) — it drives the app version and the NSIS installer.
- `src-tauri/Cargo.toml` `version` is kept in sync (`2.0.0`).
- `backend/server.py` `APP_VERSION` (`"2.0"`) is the API/`/api/health` version (informational; independent of the installer).
- `frontend/package.json` `version` (`0.1.0`) is **not** used for packaging — ignore it.

**Before a release:** bump `tauri.conf.json` `version` and mirror it in `Cargo.toml`. No other file needs changing for the installer version.

## Windows build automation
`scripts/build_windows.ps1` runs the whole chain (deps → React build → PyInstaller
one-dir → stage into `resources/backend/AkashaForgeBackend/` → `tauri build` → NSIS).
Flags: `-SkipBackend` (reuse `backend/dist`), `-NoInstaller` (`tauri build --no-bundle`).
Native Windows acceptance steps: `WINDOWS_ACCEPTANCE_CHECKLIST.md`.

## Runtime behaviour (implemented in `src/lib.rs`)
- **Data dir:** OS app-data (`%APPDATA%\com.akashaforge.desktop` via Tauri) →
  `AKASHA_DATA_DIR`. All mutable data (`database/ storage/ projects/ cache/
  logs/`) is created there by the backend — never beside the exe/resources.
- **Port:** a free `127.0.0.1` port is chosen at launch (no hard-coded 8001).
- **Sidecar env:** `AKASHA_HOST=127.0.0.1`, `AKASHA_PORT=<chosen>`,
  `AKASHA_DATA_DIR=<app data>`, `STORAGE_BACKEND=local`,
  `AKASHA_DB_BACKEND=local`, `DB_NAME=akasha_forge`, `AKASHA_SECRET_KEY=<see below>`.
- **Secret:** the backend self-provisions its Fernet **master key** via the
  AF-DESKTOP-007 secure vault (`keyring` → Windows Credential Manager / DPAPI),
  generated once per install and reused. The Tauri shell passes **no** secrets —
  no `AKASHA_SECRET_KEY`, no provider keys — nothing sensitive on the command
  line or in the injected runtime config. Provider API keys stay encrypted in the
  local DB with this master key.
- **Handshake:** bounded 30 s `/api/health` poll before the window opens; on
  failure the window shows a startup-error message (no blank/hung app).
- **Injection:** `window.__AKASHA_RUNTIME_CONFIG__ = {desktop:true, backendUrl,
  appDataDir}` via `initialization_script` (runs before the React bundle) — reuses
  the AF-DESKTOP-002 `runtime.ts` resolver; no second URL system.
- **Shutdown:** on exit the shell SIGINT/terminates the single backend child and
  waits — no orphan processes; SQLite/MontyDB left consistent.
